## 2. 数据库与 API 架构（1:10 - 4:30）— ULO3

**【画面】** `api/database/schema.sql`，从顶部开始缓慢向下滚动。

> "我先讲数据库，因为其它所有东西都建立在它之上。
>
> 这个 schema 文件分成两部分。第一部分是我在评估二保留的模型：机构
> organisations、分类 categories、场地 venues、活动 events 和活动要点
> event_highlights。一个机构可以办很多场活动，一个分类下有很多场活动，一个
> 场地可以承办很多场活动，所以它们都是一对多关系。一场活动有很多条要点，这是
> 一张子表，主键是「活动 + 展示顺序」的复合主键。
>
> 第二部分是评估三新增的：registrations 报名表。这张表回答的问题是「谁报名了
> 哪场活动」。
>
> 我的设计是这样的：主键用自增的代理键 `registration_id`，因为预订编号是给人看
> 的，不应该拿来当数据库主键。表里保存报名人的名、姓、邮箱、电话、
> `ticket_quantity` 购票数量、`registration_date` 报名时间、可选的备注，以及
> confirmed / cancelled 两种状态。
>
> 最关键的一列是 `event_id`，它是指向 events 表的外键，并且设置了
> ON DELETE RESTRICT。这带来两个保证：第一，关系是「一场活动对应多条报名」；
> 第二，已经有报名记录的活动**永远不会被误删**——就算是直接执行 SQL 也删不掉。
>
> 任务说明里的业务规则——「同一个人可以报名多场活动，但同一场活动只能报名
> 一次」——我用 `event_id` + `attendee_email` 的联合唯一键来实现。如果有人用
> 同一个邮箱对同一场活动重复报名，MySQL 会直接拒绝，API 再把它转换成友好的
> 409 提示，而不是让程序崩溃。
>
> 我还给 `event_id` 和 `registration_date` 建了联合索引，因为活动详情页永远
> 是「查某一场活动的报名、按购买时间倒序」，有了这个索引就是一次索引扫描。
>
> 文件最后创建了应用程序账号。评估二里 API 只读数据，所以账号只有 SELECT；
> 现在 API 需要增删改，所以授权扩展为 SELECT、INSERT、UPDATE、DELETE，但**刻意
> 不给** CREATE / ALTER / DROP，也没有 GRANT OPTION——这样应用永远改不了自己的
> 表结构。"

**【画面】** `api/src/app.js`。

> "Express 应用本身刻意写得很薄：用 Helmet 加安全头，允许两个开发来源的 CORS，
> 提高 JSON 体积上限，然后按资源挂载路由。注意这里**没有**任何模板引擎、没有
> 服务端渲染——它是一个纯 JSON 服务，这正是任务说明要求的。"

**【画面】** `api/src/routes/events.js`，再切到 `registrations.js`。

> "每个路由文件都是同样的三步：校验输入、调用 service、返回响应。service 层是
> 唯一直接操作 MySQL 的地方，所以路由文件里看不到 SQL 字符串。这里可以看到删除
> 路由：它调用 service，service 先检查这场活动是否还有报名记录，如果有，就抛出
> 409 Conflict，并带上解释删除被阻止原因的信息。"

**【画面】** 浏览器打开 `localhost:3000/api`，再打开
`localhost:3000/api/events/search?location=Newcastle&sort=date`。

> "这个 API 是自带文档的：打开 `/api` 就能看到全部端点列表。这里是直接在浏览器
> 里测试搜索端点——它就是搜索页用的那个端点。"

## 3. 数据流：从一次点击到屏幕（4:30 - 7:30）— ULO1

**【画面】** `clientside/src/app/core/api.service.ts`，再切到
`clientside/src/app/pages/register/register-page.ts`。

> "第二个问题：数据流。我完整跟一条链路——一位访客报名参加活动。
>
> 访客打开活动详情页，点「Register for this event」。这个按钮是一个路由链接，
> 把活动 id 放在查询字符串里带过去；报名页从 URL 里读出 `eventId`，这正是任务
> 说明允许的做法。进入报名页后它会立刻调用 API 拉取这场活动，所以页面上的活动
> 摘要永远是最新数据，而不是一份拷贝。
>
> 访客填完表单点确认时，页面**不会马上发送请求**，而是先做自己的校验：名、姓、
> 邮箱格式、电话、购票数量，并且还会把申请票数和活动剩余容量做比较。只要有
> 问题，对应字段会被标红并自动获得焦点，**不会发出任何网络请求**。这就是整个
> 项目统一使用的「先校验再发送」模式。
>
> 表单合法后，页面调用共享的 API 服务。这个服务是全站唯一的 API 封装——API
> 地址只在这里配置一处，所以将来部署换地址只需要改一个常量。"

**【画面】** `api/src/utils/validation.js` 中报名相关部分。

> "在服务端，请求会被**重新校验一遍**，因为浏览器永远不可信。validation 模块
> 集中了所有规则：邮箱正则、电话正则、1 到 100 的票数区间、姓名长度限制。随后
> service 会先用 SQL 查剩余容量，再执行插入。"

**【画面】** `api/src/services/registrationService.js`。

> "插入语句是参数化的：预订编号、报名人信息和票数都用占位符传参，**绝不拼接**
> 进 SQL 字符串。这就是防 SQL 注入的关键；活动查询构建器里也是同样的风格——筛选
> 条件被组装成一个条件数组和一个参数值数组。"

**【画面】** `clientside/src/app/pages/event-detail/event-detail-page.html`
中报名表格附近。

> "响应回来后，页面显示确认信息，并按照任务说明完成跳转——把访客带回活动页，
> 让他立刻看到自己的报名出现在列表里。
>
> 这就是评估三在活动页上的另一个新增功能：报名列表。注意三点：数据来自独立的
> 端点 `GET /api/events/:id/registrations`，并且是**在服务端**按最新购买时间
> 排序的；渲染用的是 Angular 的 `@for` 结构，完全没有用 innerHTML 拼字符串；
> 而且它是一个真正的 HTML 表格，带 caption 供屏幕阅读器使用，不是一堆 div。"

**【画面】** 浏览器中的活动详情页，表格可见。

> "所以一次完整往返是：浏览器点击 → 校验后的请求 → 参数化 SQL → JSON 响应 →
> Angular 用数据生成 DOM 元素。整个过程中，页面里没有任何硬编码内容。"
